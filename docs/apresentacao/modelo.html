01 — Visão geral

O que é o projeto

O Dashboard Operacional é um painel de controle no navegador. Ele reúne o estado de uma operação distribuída em quatro seções (visão geral, ativos, alertas e eventos) e destaca o que exige atenção.

Uma operação fictícia serve de cenário: 40 ativos (sensores ópticos, térmicos, acústicos e sísmicos; veículos de patrulha, logística e reconhecimento; estações fixas) espalhados em cinco regiões. O painel mostra quantos estão online, a latência média, o volume de eventos recebidos por segundo e os alertas ainda não tratados. O operador pode filtrar, buscar, ordenar e marcar alertas como reconhecidos.

Ainda não há servidor nem banco de dados. Os números vêm de um gerador de dados fictícios realistas que imita uma API, com tempo de resposta, falhas e respostas vazias. Assim dá para ver todos os estados da interface antes de ligar o painel a uma fonte real.

Finalidade

  • Mostrar a situação de uma vez: indicadores, tendências e pendências na mesma tela.
  • Ajudar a priorizar: ativos com problema e alertas pendentes aparecem primeiro, com a gravidade codificada em cores.
  • Servir de base para um produto real: a camada de dados é isolada, então dá para trocar o gerador fictício por uma API sem reescrever a interface.

02 — O problema

Muitos ativos, pouca visibilidade

Uma frota distribuída de equipamentos gera um fluxo constante de medições, falhas e avisos. Sem um ponto central, a equipe de operação perde tempo para entender o que está acontecendo.

Informação espalhada

Status, latência, alertas e histórico de eventos ficam em lugares diferentes, e a visão de conjunto se perde.

Difícil priorizar

Quando tudo chega junto, um alerta crítico pode ficar escondido entre avisos de rotina.

Sem noção de tendência

Um número isolado não diz se a situação melhorou ou piorou em relação ao período anterior.

Pendências sem dono

Sem registrar que um alerta foi visto, não fica claro o que ainda precisa de ação.

03 — Proposta de valor

Clareza para decidir rápido

O painel organiza a operação por urgência e mantém a interface sóbria: as cores existem para sinalizar estado, não para enfeitar.

BenefícioComo o projeto entrega
Situação em segundosQuatro indicadores com a variação em relação ao período anterior, coloridos em verde quando a mudança é boa e em âmbar quando é ruim.
Prioridade evidenteAtivos offline e degradados aparecem no topo da tabela. Alertas pendentes vêm antes dos reconhecidos. Vermelho só para o que é crítico.
Ação no próprio painel“Reconhecer” um alerta atualiza o contador de pendentes, o sino de notificações e o status geral do sistema.
Encontrar qualquer itemUma busca única filtra ativos, alertas e eventos, ignorando acentos e maiúsculas (“estacao” encontra “Estação”).
Confiável em falhasSe uma atualização falhar, os últimos dados continuam na tela, com aviso e botão “Tentar novamente”.
Para todos os usuáriosFunciona pelo teclado, anuncia mudanças para leitores de tela, tem contraste verificado e se adapta ao celular.
Pronto para crescerA origem dos dados é isolada: uma API real pode substituir a simulada sem mudar os painéis.

04 — Funcionalidades

Reconhecer alertas e acompanhar pendências

Reconhecer um alerta significa dizer “já vi, estou cuidando”. Um clique atualiza o painel inteiro de forma coerente.

Efeito de um reconhecimento
AÇÃO
Operador clica em “Reconhecer”
Na lista de alertas ou no sino de notificações.
→
01
Alerta vai para o fim da lista
Aparece esmaecido, com a marca “Reconhecido”.
→
02
KPI de pendentes é recalculado
Inclusive a variação em relação ao período anterior.
→
03
Sino e status do sistema mudam
Sem crítico pendente, o sistema volta a “Operacional”.

Navegar por qualquer lugar

  • Endereços próprios: cada seção tem sua URL, e o filtro de status dos ativos vai junto no link.
  • “Ver todos”: os painéis resumidos da visão geral levam à lista completa da seção.
  • Teclado: / abre a busca, Esc fecha menus e limpa a busca, e o foco nunca se perde depois de reconhecer um alerta.

04 — Funcionalidades

No celular

O layout se reorganiza para telas pequenas. Testes no navegador real conferem as larguras de 360, 768 e 1440 pixels.

O que muda em telas pequenas

  • A barra lateral vira um menu que abre pelo ícone ☰ e fecha com Esc, devolvendo o foco ao botão.
  • Indicadores e painéis ficam empilhados em uma coluna.
  • Os rótulos dos eixos do gráfico nunca ficam cortados.
  • A tabela de ativos rola dentro do próprio painel, sem empurrar a página para os lados.
  • O status do sistema fica só com o ponto colorido. O rótulo continua disponível para leitores de tela.

Estados da interface

Um painel profissional precisa se comportar bem quando os dados demoram, não existem ou falham. Cada situação tem uma resposta visual própria.

Um endereço inexistente leva à página “Página não encontrada”, com link de volta para a visão geral.

Demonstração embutida. Basta acrescentar ?simular=erro, ?simular=vazio ou ?simular=lento ao endereço para forçar cada estado. Foi assim que as capturas desta página foram geradas.

06 — Como o sistema funciona

O caminho dos dados

Toda a tela depende de um único pacote de dados por período. A ordem abaixo explica o que acontece desde a escolha de um filtro até a atualização dos painéis.

Fluxo de uma atualização
01 · FILTRO
Usuário escolhe o período
24 h, 7 dias ou 30 dias.
→
02 · PEDIDO
Provedor de dados pede à API
Um pedido ainda em andamento é cancelado.
→
03 · API SIMULADA
Gera os dados fictícios
Após ~0,4 s, ou 2 s no modo lento. Pode falhar ou vir vazia sob demanda.
↓
06 · TELA
Busca e severidade filtram as listas
Na própria tela, sem novo pedido.
←
05 · PAINÉIS
Cada painel decide seu estado
Carregando, com dados, vazio, erro ou recarregando.
←
04 · SESSÃO
Reconhecimentos são aplicados
Alertas, KPI de pendentes e status do sistema ficam coerentes.

Dados fictícios, mas realistas

O gerador usa um sorteio com semente fixa e uma data de referência fixa (16/10/2026, 12h UTC). A mesma tela aparece toda vez, o que facilita testes, demonstrações e comparações.

Os números seguem proporções plausíveis: 80% dos ativos online, 15% degradados e 5% offline, latências maiores nos ativos com problema e uma curva de ingestão que varia ao longo do dia.

Robustez embutida

  • Uma resposta atrasada nunca sobrescreve a mais recente.
  • Valores inválidos (NaN, infinito) aparecem como “—”, nunca como texto quebrado.
  • Números e datas seguem o padrão brasileiro (1.199 ev/s, “há 5 h”).
  • Os gráficos carregam à parte. Se falharem, só o painel deles é afetado.

Estados de um painel

Carregando
Sem dados ainda: blocos de espera.
Com dados
Conteúdo normal, interativo.
Vazio
Pedido bem-sucedido, mas sem itens: mensagem explicativa.
Recarregando
Dados anteriores visíveis e esmaecidos enquanto chega o novo período.
Desatualizado
A recarga falhou, mas os dados anteriores continuam visíveis.
Erro
Nada para mostrar: “Dados indisponíveis” e aviso com nova tentativa.

Para quem é

O painel foi pensado para quem acompanha uma operação em turnos e precisa reagir rápido. O menu de perfil identifica o usuário como “Operador · Turno A”.

Usuário principal

Operadores de turno

Acompanham a frota, reconhecem alertas e investigam eventos durante o expediente.

Gestão

Supervisores

Usam os indicadores e as tendências para avaliar a saúde geral e comparar períodos.

Técnico

Equipes de desenvolvimento

Partem desta base para construir um painel real, ou a usam como referência de boas práticas.

Possíveis aplicações

O modelo de dados (ativos com tipo, região, status e latência; alertas com severidade; eventos com autor) é genérico o suficiente para vários domínios. Os exemplos abaixo são aplicações possíveis, ainda não implementadas.

ÁreaExemplo de uso
Redes de sensores (IoT)Monitorar sensores ambientais, industriais ou sísmicos, com queda de sinal, bateria e temperatura.
Frotas e logísticaAcompanhar veículos por região, com latência de comunicação e rotas recalculadas.
Segurança e vigilânciaCentros de controle com sensores ópticos e acústicos e veículos de patrulha, como no cenário simulado.
Infraestrutura de TIServidores e serviços no lugar dos ativos, com ingestão de eventos e alertas de disponibilidade.
Utilidades e energiaEstações remotas com falha de energia, telemetria e manutenção programada.
EnsinoMaterial de estudo de React, TypeScript, testes e acessibilidade num projeto completo e coerente.
Identidade visual. O tema escuro, a tipografia técnica e os acentos em verde e âmbar seguem a especificação do projeto, inspirada em softwares operacionais de alto nível, sem copiar marcas ou layouts. O visual sóbrio reduz o cansaço em turnos longos e deixa as cores livres para sinalizar estado.

08 — Diferenciais e evolução

O que distingue o projeto

Acessibilidade de verdade

Análise automática em todas as páginas e estados, contraste testado, uso completo pelo teclado, foco que não se perde ao reconhecer alertas e gráfico com versão em tabela.

Coerência dos dados

Reconhecer um alerta recalcula indicador, contador e status do sistema. Tabela, gráfico e listas nunca se contradizem.

Pensado para falhas

Seis estados de painel tratados, simulação de erro, vazio e lentidão pela URL e dados preservados quando uma atualização falha.

Base sólida para crescer

Origem dos dados isolada, tipos compartilhados, componentes reutilizáveis e mais de {{unitTestsRounded}} testes protegendo cada mudança.

09 — Conclusão

Uma base pronta para a operação real

O Dashboard Operacional mostra que um painel denso de informação pode ser, ao mesmo tempo, claro, acessível e confiável.

Em uma tela, o operador vê como está a frota, o que mudou em relação ao período anterior e o que precisa de ação. A interface trata com o mesmo cuidado o caminho feliz e as situações difíceis (lentidão, falha, ausência de dados), e todo o comportamento é protegido por testes automatizados.

O principal passo que falta é conectar uma fonte de dados real. A arquitetura foi preparada para isso: a origem dos dados é uma peça isolada e o resto da aplicação não precisa saber de onde as informações vêm.

Para o usuário

Decidir mais rápido

Prioridades evidentes, ações no próprio painel e leitura confortável em turnos longos.

Para o negócio

Menos risco

Alertas críticos não se perdem, e falhas de comunicação não deixam a tela em branco.

Para a equipe

Evolução segura

Código organizado, tipado e testado, com regras de projeto documentadas.

Escopo e limitações

O que este documento não cobre, e por quê

  • Sem dados reais: todos os números, nomes e operadores são fictícios, gerados pelo próprio app. O documento não traz métricas de uso ou de desempenho em produção.
  • Sem servidor, login ou publicação: o repositório contém só a aplicação no navegador. Não há instruções de implantação, ambiente de produção ou integração com sistemas externos.
  • Público e problema inferidos: não há documento de requisitos de negócio. O problema e o público foram deduzidos da especificação de design, do cenário simulado e da interface. As aplicações listadas são possibilidades.
  • Versão e documentação: o projeto está na versão 0.0.0, sem notas de lançamento. Este documento foi escrito a partir do código, dos testes e de docs/design.md e docs/plano.md.
